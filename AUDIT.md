# CampusForge — аудит продукта и готовности стартапа к запуску

**Дата:** 8 октября 2026 года.  
**Основа:** текущая рабочая копия, `main`, HEAD `b9bf84099474045715ed86405f64ea6172de5833`, включая существовавшие незакоммиченные пользовательские изменения.  
**Режим:** read-only аудит; исправления приложения и обновления зависимостей не выполнялись. В репозитории создан только этот отчёт. Проверки установки, сборки и UI проводились в отдельной scratch-копии без рабочих `.env` и реальных пользовательских данных.

## 1. Краткий вывод

**CampusForge — академический workspace с задачами, заметками, документами и инструментами подготовки к учёбе. По фактическому состоянию это технически развитый pre-pilot прототип, а не готовый учебный AI-сервис.** После R1–R4 появилась заметно более надёжная техническая основа, но ключевой пользовательский экран остался демонстрационным.

Главный разрыв: серверная цепочка загрузки, парсинга и устойчивой AI-генерации существует, однако кнопки генерации на странице документа **не используют её**. Они показывают шаблонный summary по имени файла и фиксированный набор общих карточек. При этом реально сохранённые summary, наборы карточек и статусы AI jobs передаются странице, но игнорируются клиентским компонентом. Это подтверждено кодом и отдельным браузерным воспроизведением, а не предположением о качестве модели.

### Три главных препятствия для успеха

1. **Пользователь пока не получает обещанную основную ценность.** Демонстрационные ответы, анализ вложений без чтения их содержимого и фиктивный dashboard выглядят как реальные результаты. На такой основе нельзя честно проверять полезность или брать оплату.
2. **Не выделен один покупаемый результат и не доведён путь к нему.** Лендинг обещает учёбу, команды, дедлайны и карьеру одновременно; dashboard ориентирован на запуск программного продукта. На мобильном исчезает навигация по workspace. Неизвестно, какой конкретный сегмент действительно нуждается в CampusForge.
3. **Есть качественная инженерная база, но нет свежего доказательства эксплуатационной готовности и бизнес-спроса.** Полный real-stack сценарий, восстановление бэкапов, фактическая себестоимость, активация, удержание и готовность платить в этом аудите не установлены. Workspace-бюджет не заменяет общий лимит расходов сервиса.

**Допуск сейчас:** честно обозначенный показ прототипа и интервью на публичных/разрешённых материалах. **Не рекомендован сейчас:** самостоятельный полноценный пилот с личными документами или публичный платный запуск. Закрытый пилот возможен после подключения одного полезного сценария и проверок допуска из раздела 7. Отсутствие подтверждённых P0 в доступных проверках не является заключением об отсутствии уязвимостей.

### 1.1. Для кого и какую задачу стоит проверить первой

**Рабочая гипотеза, не установленный рынок:** студент одного конкретного курса, которому скоро сдавать экзамен и который уже располагает текстовыми конспектами/лекциями. Его задача: быстро получить проверяемую выжимку материала, потренироваться на вопросах и вернуться к трудным темам.

Минимальный полезный путь:

> Открыть сервис → загрузить разрешённый короткий конспект → увидеть состояние обработки → получить summary и карточки именно по его содержимому → проверить несколько ответов → сохранить набор → продолжить подготовку позже.

Первый результат — не регистрация, красивый ответ или клик Generate. Это **содержательно правильный материал, по которому пользователь действительно провёл учебную сессию**.

Не стоит одновременно выбирать студентов, исследователей, команды разработчиков и соискателей. Страна, язык, предмет, тип экзамена, бюджет и возраст первой аудитории неизвестны. Русскоязычность этого отчёта не доказывает, что продукт нужно запускать именно на русском языке.

## 2. Что уже сделано хорошо

1. **Сборка и production packaging теперь проверяемы.** Runtime Node/pnpm зафиксированы; shared/db/ai собираются; Prisma Client включён в release artifact. Свежий production-only smoke действительно загрузил runtime и PDF parser. Это уменьшает вероятность ситуации «работает только на ноутбуке разработчика». Доказательства: `package.json:47-49`, `scripts/package-release.mjs:25-55`, `scripts/probe-release.mjs:31-87`, свежие `quality-final/release-results.json` и `release-smoke.log`.
2. **Серверная граница доверия устроена разумно.** `requireAuth` требует строковый user ID, `requireWorkspaceMember` проверяет составной ключ user/workspace; document queries дополнительно ограничены workspace и ACTIVE lifecycle. JWT update читает профиль из БД, а не доверяет client session fields. Доказательства: `apps/web/src/server/services/auth-helpers.ts:11-42`, `apps/web/src/lib/auth.ts:40-55`, `apps/web/src/server/queries/document.ts:52-58`.
3. **Password abuse не оставлен без контроля.** Есть атомарные Redis budgets, timeout, ограничения по источнику/аккаунту, fail-closed поведение и обработка bcrypt byte limits. Это полезнее для старта, чем декоративная CAPTCHA без серверных ограничений. Доказательства: `apps/web/src/lib/auth-rate-limit.ts:9-35,63-84,114-135`, `apps/web/src/lib/auth.ts:64-99`. Реальная proxy/header конфигурация всё равно требует deployment-проверки.
4. **R3/R4 решают настоящие lifecycle-проблемы, а не только happy path.** В коде есть durable obligations/outbox, leases, условная фиксация результатов, cancellation при удалении и idempotent admission. Неопределённый внешний outcome не просто скрывается под обычной повторной попыткой. Это хорошая база для контроля потери документов и повторных расходов. Доказательства: `packages/db/src/document-lifecycle.ts`, `packages/db/src/ai-lifecycle.ts:220-299`, `apps/worker/src/jobs/ai-operation.ts`; свежие package regressions проходят. Проверка фактических распределённых crash windows в этом аудите ограничена.
5. **Локальная приватность после R2 учитывает аккаунт, workspace и stale callbacks.** Content cache scoped по identity, есть lease/epoch, cleanup перед logout, cross-tab revocation и защита от поздней записи старого состояния. Это особенно полезно на общих студенческих устройствах. Доказательства: `apps/web/src/lib/privacy.ts`, `apps/web/src/components/auth/authenticated-privacy-boundary.tsx`, `docs/releases/R2-privacy.md:8-61`, свежие browser regressions. Browser storage не является шифрованием и не заменяет account deletion.
6. **В нескольких точках есть честная обратная связь.** Documents empty state ведёт к Upload; диалог явно описывает очередь обработки, лимит и network/server ошибки; parsing pending/failed отображаются отдельно. Доказательства: `apps/web/src/components/document/document-list.tsx:79-94`, `upload-document-dialog.tsx:90-129`, synthetic screenshots pending/failed. Это стоит сохранить при подключении настоящей AI-цепочки.

Сильные стороны выше — инженерные и интерфейсные факты. **Ни одна из них не подтверждает спрос, учебную эффективность, выручку или конкурентное преимущество.**

## 3. Реестр проблем

### Обозначения и оценка

- **Подтверждено:** установлено кодом, исполняемой проверкой или наблюдением оригинального компонента.
- **Гипотеза влияния:** предполагаемое влияние на поведение/конверсию; пользователей и измерений для проверки нет.
- **Непроверенный риск:** необходимо закрыть перед допуском, но нельзя утверждать, что production уже сломан или данные потеряны.
- P0 — критическая угроза данным/работе; P1 — основной сценарий или допуск к запуску; P2 — заметное ухудшение; P3 — улучшение.
- Трудоёмкость — приблизительные человеко-дни одного разработчика, знакомого с проектом, без ожидания внешних доступов. Уверенность в этих сроках преимущественно средняя; это не обязательство выполнить всё за неделю.

### F01. Основная генерация документа осталась демонстрационной

**Категория:** функциональность / продукт. **Приоритет:** P1. **Статус:** подтверждено кодом и браузером.

- **Доказательство:** `apps/web/src/components/document/document-detail-view.tsx:100-142,167-224`; серверная страница передаёт настоящие summary/jobs/sets в `apps/web/src/app/(dashboard)/w/[workspaceId]/documents/[documentId]/page.tsx:33-47`, но `DocumentSession` их не использует. Действие `generateSummaryAction` существует в `apps/web/src/server/actions/summary.ts:15-32`.
- **Воспроизведение:** оригинальный компонент получил synthetic document с parsed text и сохранённым контрольным summary. UI показал «No summary yet». После Generate показал обзор по filename, «8–10 min read» для 93-байтного файла и шесть шаблонных общих карточек. В записанном сетевом потоке были только auth-session GET, не admission generation. `ux/ui-probe.json`, cases `desktop-document-persisted` / `document-generation`.
- **Влияние:** студенту показывается не содержание его конспекта; нельзя проверить основной полезный результат. Сохраняемые локально demo cards не становятся настоящим study set.
- **Исправление:** подключить существующие actions с устойчивым idempotency key; показывать receipt/job states и сохранённые server results; изучение вести в настоящий набор; убрать незаявленную симуляцию из production-пути. Не строить второй AI backend.
- **Трудоёмкость:** 3–5 дней вместе со статусами и regression/E2E проверками. **Уверенность:** высокая в дефекте, средняя в сроке.

### F02. AI Assistant изображает модели и анализ файлов, которых в этом пути нет

**Категория:** продукт / доверие. **Приоритет:** P1 для публично обещанной функции; можно полностью исключить из первого пилота. **Статус:** подтверждено кодом.

- **Доказательство:** `apps/web/src/lib/assistant/engine.ts:1-6,829-862` — синхронный выбор заготовок и «analysis» по metadata файла; `apps/web/src/components/assistant/chat-input.tsx:77-105` — вложение сохраняет имя/тип/размер/preview и fake progress, не извлечённый текст. `assistant-app.tsx:12` импортирует этот engine.
- **Влияние:** ответы и заявления «проанализировал файл/изображение» не обоснованы его содержимым. Модельный selector не доказывает вызов перечисленных моделей. Конверсию таких demo responses нельзя считать спросом на AI.
- **Исправление:** для пилота убрать общий Assistant из основной навигации и обещаний либо явно обозначить как интерактивный demo. Реальный source-grounded assistant добавлять только по результатам спроса; не подключать несколько провайдеров сейчас.
- **Трудоёмкость:** 0,5–1 день для честного ограничения; полноценный chat — отдельная неопределённая по объёму задача. **Уверенность:** высокая в факте, средняя в влиянии на конверсию.

- `postcss-selector-parser 6.1.4`: moderate, цепочка Tailwind/build tooling; patched 7.1.6. Существующий override `package.json:60` не закрывает это новое affected range.[12]
- **Влияние:** нужна актуальная политика зависимостей и оценка обработки недоверенных source maps/selectors/patterns. Само presence в `--prod` не доказывает достижимый HTTP DoS, а dev advisory не равен утечке пользовательских документов.
- **Исправление:** проследить реальный runtime call path; совместимо обновить исправляемые transitives с frozen-lockfile + full gates; для braces без patch — убрать уязвимый недоверенный ввод/выбрать безопасную цепочку либо документировать ограниченный по сроку tooling risk. Добавить периодический audit/alerts. Не запускать слепой `audit fix --force` и не принудительно менять major без тестов.
- **Трудоёмкость:** 0,5–1 день на triage, совместимость может расширить срок. **Уверенность:** высокая в версиях/severity, низкая в достижимости из приложения. Зависимости в рамках аудита не менялись.

### F20. Document queries читают лишние данные и не ограничивают список

**Категория:** производительность / поддерживаемость. **Приоритет:** P3, не blocker малого пилота. **Статус:** подтверждено кодом; bottleneck не измерен.

- **Доказательство:** `apps/web/src/server/queries/document.ts:30-45` делает findMany без select/take; map затем оставляет только metadata. Detail `:52-73` возвращает parsedText/storageKey клиентскому компоненту, который сейчас не использует текст для реальной генерации. Recent query ограничивает take, но тоже читает всю строку.
- **Влияние:** лишние DB transfer/memory и сериализация текста; при больших корпусах цена list request растёт с количеством и размером документов. В текущем маленьком пилоте это не основание строить новую инфраструктуру.
- **Исправление:** metadata select в lists; не отправлять raw text/storage internals клиенту без необходимого UI; простая pagination только когда реальные объёмы этого требуют. Проверить payload size после F01.
- **Трудоёмкость:** 0,25–0,5 дня на select/payload; pagination отдельно. **Уверенность:** высокая в форме запросов, низкая в текущем влиянии на latency.

### Приоритет допуска

- **До осмысленного пилота:** F01, F03, F04; честно исключить/маркировать F02; закрыть допуск F15–F18 на выбранной ограниченной аудитории. Удобство статусов и реальные лимиты F06–F09 желательно включить в этот же небольшой путь.
- **До публичного расширения:** triage F19, реальная privacy/retention и подтверждённый общий spend cap, доступная поддержка, повторный real-stack прогон.
- **Не блокировать первую проверку спроса:** полный chat, сложный SRS, career/research/team расширения, массовая pagination и масштабирование.

- **Активация:** пользователь загрузил поддерживаемый материал, получил реальный persisted result и завершил первую мини-сессию, например просмотрел пять cards. Это измеримое рабочее определение; проверить, соответствует ли оно ощущению пользы.
- **TTV:** время от начала первого upload до первой полезной study-сессии; отдельно время регистрации и анкеты. Не выдавать demo timer за AI latency. Начальный экспериментальный ориентир — полезный результат менее чем за пять минут на поддерживаемом коротком материале.
- **Повторное использование:** добровольная полезная сессия в другой день, а не повторный login или переход из founder reminder. Для экзаменационного сценария важнее подготовка в несколько дней и повтор на следующем экзамене, чем формальное ежедневное DAU.
- **D7:** считать только по активированным участникам, за которыми есть минимум семь дней наблюдения; явно определить окно возврата. При маленьком N показывать людей и denominators, а не красивый процент без основы.
- **Качество:** доля фактических ошибок в проверенной выборке, доля отброшенных/исправленных cards, принятие результата для реальной подготовки. Shape-valid JSON не доказывает предметную правильность.
- **Оплата:** реальные payments относительно одинаково сделанных offers; отдельно цены/пакеты/cohorts. Ответ «готов заплатить» в интервью — не покупка.
- **Экономика:** provider usage/cost, failed/uncertain attempts, storage/worker, support time, fees/refunds. Count generations не заменяет cost per accepted useful package.
- **Привлечение:** qualified contacts → upload → activation → paid; учитывать время основателя на интервью/onboarding как стоимость канала. Не смешивать знакомых тестировщиков, demo traffic и самостоятельных пользователей.

### 4.6. Монетизация и расходы

Предпочтительно сначала проверить **ограниченный пакет подготовки к одному экзамену/теме**, а не unlimited подписку. Пользователь платит за принятый учебный результат и удобство, не за факт API-вызова.

Возможные гипотезы предложения:

- **Пакет:** фиксированное число коротких документов/наборов и ограниченная регенерация. Тестовый диапазон 3–5 USD либо осмысленный локальный эквивалент — гипотеза эксперимента, не оценка готовности студентов платить.
- **Подписка 5–10 USD:** проверять только если наблюдаются регулярные учебные сессии вне одного экзамена. Указать лимиты, а не обещать безлимит. Цена тоже гипотеза.
- **Группа/преподаватель:** отложить до самостоятельного использования и приглашений; институциональные продажи сейчас добавят обязанности раньше доказанной ценности.

Для выбранного в коде default `gpt-4o-mini` официальная стандартная text pricing на дату проверки — 0,15 USD за миллион входных и 0,60 USD за миллион выходных токенов.[6] Расчёт ниже выполнен программно, без cached/batch discounts:

| Условный workload                         | Только AI text tokens, USD |
| ----------------------------------------- | -------------------------: |
| 10000 input + 1000 output, один вызов     |                     0,0021 |
| Два таких вызова: условно summary + cards |                     0,0042 |
| 1000 таких пар                            |                       4,20 |
| 50000 input + 2000 output, один вызов     |                     0,0087 |

Это **иллюстрация**, не реальные документы, invoices или unit economics CampusForge. Последний workload превышает текущий default admission; он приведён для чувствительности затрат, а не как поддерживаемая возможность. Input/output токены гипотетические; верхняя byte-estimate из F07 не равна реальному billed token count.

В коде default workspace allowance равен 1000000 USD micros, то есть 1 USD, operation ceiling — 100000 micros, то есть 0,10 USD; concurrency — 2. Консервативный reservation для default 16000 input / 2048 output / 3 attempts по этим ставкам приблизительно 0,010887 USD, с округлением вверх до micros (`packages/shared/src/env.ts:26-49`, `packages/ai/src/pricing.ts:58-76`). **Reservation не является invoice, daily quota или глобальным ограничением сервиса.**

Реальную устойчивость определяют также постоянные DB/hosting/storage расходы, parser CPU/RAM, failures/uncertain attempts, дополнительные model calls, support, payment fees/refunds и привлечение. Эти расходы и конфигурация deployment неизвестны; точную месячную маржу или бюджет хостинга назначать нельзя. До роста вести простой ledger реальных invoices + полезных пакетов + времени поддержки, пересматривать pricing version и общий spend ceiling.

## 5. Что не стоит делать сейчас

- Подключать несколько LLM providers и развивать selector ради количества моделей. Первый пилот должен доказать качество одного source-specific результата.
- Делать универсального multi-agent помощника, autonomous research, сравнение статей, career coach и resume review одновременно.
- Строить собственный сложный SRS/адаптивный tutor до наблюдения повторных study-сессий. Сначала проверить ручной прогресс или простой Resume.
- Переписывать рабочую durable queue архитектуру на другую ради моды. R3/R4 уже дают полезную основу; задача — подключить её к UI и проверить runtime.
- Добавлять Kubernetes, microservices, multi-region, vector DB или отдельный data warehouse без измеренного bottleneck. Один контролируемый deployment web+worker с понятными backups/лимитами достаточен для проверки спроса.
- Делать native mobile app вместо исправления navigation/layout текущего web UI.
- Обещать все форматы, OCR любых PDF и неограниченную длину. Сначала поддерживаемый corpus и ясные ограничения.
- Строить подписочный billing/tier management до первых честных оплат за следующий пакет.
- Покупать массовый трафик, нанимать growth-команду, оценивать TAM или заявлять CAC/LTV без пользователей и denominators.
- Выдавать sample workspace, hardcoded «customer feedback» и demo generations за social proof или product metrics.
- Отказываться от backup, общего spend cap и поддержки под предлогом «мы слишком маленькие». Это минимальная ответственность за реальные данные, а не преждевременное масштабирование.

## 6. План действий на 7, 30 и 90 дней

**Ресурсная предпосылка:** один full-stack разработчик и доступное время основателя на исследование/поддержку. Если это один человек, уменьшить число параллельных задач. Сроки — ориентиры, не обещание закрыть весь реестр за неделю. Расширять scope только после измерений.

### Первые 7 дней — честный узкий прототип, а не публичный релиз

**Продукт/техника:**

1. Зафиксировать один сегмент, поддерживаемые короткие материалы и основной useful action; убрать из обещаний общий Assistant, career/research/team extensions.
2. Убрать фиктивные dashboard данные; сделать upload-first старт.
3. Подключить существующую server generation к document UI с receipt/idempotency и persisted display. Добавить bounded status refresh и ясный AI input limit. При нехватке времени довести один document flow вместо полировки всех разделов.
4. Исправить mobile nav и непустой Documents layout/основные accessible actions. Assistant composer чинить только если функция сознательно остаётся в scope.
5. Подготовить disposable stack и checklist допуска; назначить владельца поддержки/расходов.

**Проверка спроса:** E1 и несколько материалов E2 параллельно, без ожидания идеального приложения. Показ неработающей AI-функции не выдавать за автоматическую генерацию.

**Выход недели:** правдивый узкий demo/кандидат пилота, первые документированные проблемы пользователей и список оставшихся gates. Если real-stack/backup/privacy gates не выполнены, пилот ещё не начинать.

### До 30 дней — допуск и первая ограниченная cohort

**Продукт/техника:**

- Пройти F18 на disposable PostgreSQL/Redis/MinIO, настоящих guarded paths и контролируемом provider acceptance; повторить regression/production packaging.
- Проверить реальную subject accuracy, обработку invalid output, pending/failed/uncertain и возврат сохранённых результатов с другого окна/после login.
- Включить invite/allowlist, account/storage/global caps, минимум privacy/support/export/delete и подтверждённый restore. Завершить dependency triage F19; не игнорировать новые advisories из-за старого green audit.
- Вести ручные либо минимальные server events. Только по наблюдениям добавить Resume/исправления cards/export.

**Проверка спроса:** E3, E4, E5; целевой набор 10–15 участников, не заявляемый результат. Сравнить paid offer, качество, добровольные возвраты и поддержку.

**Выход месяца:** честное решение — продолжать узкий продукт, менять сегмент/обещание либо остановить расширение. Не считать cohort знакомых достаточным подтверждением массового рынка.

### До 90 дней — повторяемость ценности и условное расширение

**Если спрос подтверждён:**

- Повторить пилот с участниками за пределами круга основателя и на следующем экзамене/теме; проверить повторную оплату и самостоятельную активацию.
- Выбрать одну следующую способность по фактическому отказу/востребованности: long-document support, study continuity или shared course set, не все сразу.
- Нормализовать реальные costs/invoices/support, зафиксировать ограниченный платный пакет и supported corpus. Автоматизировать billing/recovery/export только там, где ручная процедура стала bottleneck.
- Сделать repeatable deploy/backup/restore и alerts для queue age, final failures, cleanup backlog, uncertain AI outcomes и spend. Расширять capacity по наблюдаемой нагрузке.

**Если спрос не подтверждён:** не компенсировать это новыми моделями и функциями; пересмотреть job/сегмент по интервью, провести меньший concierge тест либо заморозить коммерческую разработку. Отсутствие спроса — возможный результат эксперимента, не инженерный баг.

## 7. Пять следующих задач в порядке выполнения

### 1. Зафиксировать контракт пилота и убрать ложные обещания

**Результат:** один сегмент, один язык/курс, один supported corpus; upload-first экран вместо фиктивного dashboard; общий mock Assistant и неподтверждённые расширения не продаются как работающие функции.

**Критерий готовности:** человек, не знающий проекта, может объяснить обещаемый результат и следующий шаг; пустой workspace не показывает вымышленные задачи/документы; demo явно отделён от реального режима. Начать E1 до существенного расширения разработки.

**Зависимости/объём:** решение основателя; примерно 0,5–1,5 человеко-дня продуктовых/минимальных UI изменений. Это будущая задача — в ходе аудита исходники не исправлялись.

### 2. Довести реальный document-to-study flow

**Результат:** использовать имеющиеся upload/lifecycle/actions/worker, показывать actual saved summary/cards и job states; сохранять idempotency при повторе запроса; согласовать upload/AI ограничения.

**Критерий готовности:** два различающихся разрешённых текста дают отличающиеся содержательные результаты; повтор запроса с тем же key не создаёт второй logical operation; refresh/reopen показывает server result; набор открывается в Study; oversize/parse/provider failure не выглядит как успешная генерация. Проверка по исходному тексту, не только валидный JSON.

**Зависимости/объём:** задача 1 и disposable infrastructure; 3–5 человеко-дней плюс обнаруженные runtime ошибки. Paid provider — отдельный согласованный test project, не рабочие пользовательские документы.

### 3. Пройти основной путь на мобильном и клавиатуре

**Результат:** mobile menu, адаптивный непустой Documents list, корректный empty-MIME upload, доступные controls и ограниченные shortcuts study viewer. Не чинить весь optional Assistant, если его исключили из scope.

**Критерий готовности:** viewport 390×844 и desktop проходят upload → статус → результат → Study → возврат; нет horizontal overflow; разделы/workspace достижимы; Tab/Enter/Space выполняют ожидаемое действие; controls имеют accessible names; pending/failed/empty состояния видны. Добавить regression именно на эти реальные исходные компоненты.

**Зависимости/объём:** задача 2 для полного пути; около 1–2 человеко-дней.

### 4. Получить проверяемый допуск к ограниченному пилоту

**Результат:** actual real-stack acceptance + минимальная эксплуатационная и privacy процедура, с явным решением по advisories.

**Критерий готовности:** disposable A/ws1 → A/ws2 → logout → B/ws1 не раскрывает чужих данных; upload/parse/generate/reopen/delete проходят; Redis/provider outage и worker restart дают явный корректный outcome; общий cap и account/storage caps проверены; отдельный restore восстанавливает документ и результаты; support/export/delete процедура опробована на synthetic аккаунте; dependency findings исправлены либо обоснованно ограничены/приняты на срок. Fresh build/test/release evidence приложен. Только затем реальные участники с личными материалами.

**Зависимости/объём:** задачи 1–3, доступный Docker/host, test provider; примерно 3–5 человеко-дней и возможное ожидание доступов. Не использовать существующие real DB/volumes для испытаний.

### 5. Провести измеряемую учебную cohort и честный тест оплаты

**Результат:** 10–15 квалифицированных участников одного курса, наблюдение первой полезной сессии и самостоятельного возврата, сравнение с альтернативой, предложение следующего ограниченного пакета.

**Критерий готовности:** есть ledger с источником участника, supported material, TTV/activation, quality issue, voluntary return, offer/payment/refund и support time; denominators известны; опубликовано решение continue/pivot/stop по заранее записанным критериям. Не подменять фактические оплаты интервью-намерением или demo traffic.

**Зависимости/объём:** интервью можно начать сразу; реальный продуктовый пилот после задачи 4; наблюдение 7–14 дней плюс доступное время основателя. Результат спроса заранее неизвестен.

## 8. Ограничения, риски вне подтверждённого реестра и вопросы

### 8.1. Что не удалось подтвердить

- Docker daemon недоступен, поэтому текущие migrations и согласованная работа PostgreSQL/Redis/MinIO/BullMQ на disposable stack не проверены заново. Существующие release/integration отчёты учитывались как история реализации, не выдавались за свежие запуски.
- Production release smoke реально выполнен, но infrastructure readiness намеренно отсутствует. Worker module load не равен рабочим очередям.
- Не выполнены свежие actual DB registration/sign-in/onboarding/logout и сквозные CRUD разных реальных аккаунтов. Synthetic sessions и membership substitutes не заменяют эту приёмку.
- Paid AI calls не делались; реальные usage, provider retries, качество и стоимость не установлены. Synthetic контролируемый summary в UI fixture не является output провайдера.
- Не проверены deployment TLS/reverse proxy/body limits/header stripping, host firewall, secret rotation, actual rate-limit IP доверие и настройки provider project. Default `passwordRequestSource` объединяет недоверенный источник в `unknown`; при массовом signup deployment должен проверить поведение общих quotas, а не просто доверять любому forwarded header (`auth-rate-limit.ts:49-82`).
- Dev Compose содержит известные development credentials и публикует Redis/MinIO ports без loopback-привязки (`infra/docker-compose.yml:23-47`). Их значения намеренно не приводятся. Это не доказательство открытого production deployment; использовать этот compose как готовую production security конфигурацию нельзя.
- Полной secret-проверки `.env`, истории Git, внешних CI/deployment хранилищ и credentials не было. Рабочие секреты/реальные environment values не использовались. Ограниченный source token scan не нашёл выбранные форматы, но не исключает другие секреты.
- Не проводились hostile-PDF/ZIP-bomb/сильная CPU-RAM нагрузка, fuzzing parser и OS resource-limit испытания. `apps/worker/src/lib/pdf.ts:3-23` выключает eval и уничтожает parser по abort, но без hostile-corpus проверки нельзя гарантировать защищённость от любого ресурсного DoS. Для раннего пилота использовать разрешённый ограниченный corpus.
- Не проверены object storage backups/versioning, retention всех derived data/receipts, actual account erase, архивные copies и восстановление после host failure. R4 terminal path убирает input snapshot (`packages/db/src/ai-lifecycle.ts:133-134`), поэтому нельзя повторять старое утверждение, что весь AI input обязательно остаётся навсегда; full retention всё равно требует отдельной проверки.
- Мобильный/desktop осмотр выполнен в Chromium, преимущественно 390×844 и 1440×900; regression fixtures имеют собственную матрицу. Safari/iOS, реальная touch keyboard, screen reader, все languages/themes и полная WCAG проверка не пройдены. Устройство и язык первой аудитории неизвестны.
- Нет свежих нагрузочных benchmark на целевом host. Build duration и synthetic demo delay не являются пользовательской производительностью.
- Нет подтверждённых пользователей, revenue, retention, market size, CAC/LTV, paid conversion, образовательного эффекта и доступного бюджета команды. Тексты sample dashboard не восполняют эти данные.
- Доступность региональных подписок/платёжных providers и конкретные цены конкурентов не исследованы; внешнее сравнение ограничено проверенными официальными feature descriptions. Никаких claims о superior quality или более дешёвом месячном сервисе не сделано.
- При повторной проверке Quizlet Help и OpenAI Study Mode Help прямые открытия попадали под bot wall; соответствующие утверждения дополнительно сопоставлены с индексируемым текстом официальных статей. Google, Anki, API pricing/data controls и GitHub advisories прочитаны непосредственно. Полный сравнительный продуктовый benchmark не проводился.

Для передачи сохраняется отдельный evidence-архив вне репозитория: только результаты/наблюдения/скриншоты, без `.env`, cookies/session state, полных сторонних статей и real user data. Базовые дефекты можно воспроизвести из приведённых file:line и описанных synthetic inputs даже после удаления кеша.

**Итоговое решение:** не добавлять ширину продукта. Сначала превратить существующий document pipeline в честную, проверяемую учебную ценность, затем проверить её на маленькой cohort и реальной оплате. Если это не востребовано, новые модели и разделы не исправят бизнес-модель.
