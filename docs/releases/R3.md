## State machine и consistency guarantees

| Сущность      | Persisted состояния и переходы                                                                                                                     |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Upload intent | UPLOADING до S3 Put; FINALIZED атомарно с Document + PARSE task; иначе CLEANUP после expiry/отказа, затем DONE после quarantine                    |
| Document      | ACTIVE/PENDING → PROCESSING с token/lease → COMPLETED либо FAILED; ACTIVE → DELETING только с durable DELETE task                                  |
| Durable task  | PENDING → CLAIMED с atomic CAS/lease → PENDING после delivery/retry; DONE после persisted parse result/terminal failure либо окончательного delete |
| Delete        | Tombstone сразу скрывает документ; S3 Delete → short transaction physical Document delete + task DONE; failure сохраняет intent и повтор           |

У каждого upload immutable UUID; key `documents/{workspaceId}/{id}` не зависит от filename или времени. PostgreSQL uniqueness и S3 `IfNoneMatch: '*'` дополняют эту identity. Точное имя хранится в DB; необязательная encoded S3 metadata ограничена по bytes. Cleanup abandoned upload проверяет HEAD ownership metadata; чужой объект не удаляется даже при неоднозначном ответе conditional Put.

Upload ledger фиксируется **до** Put. Document, stable PARSE task `parse-{id}-v1` и FINALIZED intent сохраняются одной DB transaction. S3/Redis сетевых вызовов в этой transaction нет. Ambiguous commit проверяется через persisted intent; FINALIZED никогда не компенсируется cleanup. `201 {documentId, processingStatus:PENDING}` означает файл и обязанность parsing сохранены, а не завершённый parsing. Upload не зависит от Redis.

Dispatcher запускается в compiled worker каждые 2 секунды и допускает несколько instances. Claims/parse leases: 60 секунд; parse heartbeat: 20 секунд; Redis delivery visibility: 60 секунд. Delivery не завершает DB task: удаление/потеря BullMQ record восстанавливается повторной dispatch. Terminal queue records удаляются; DB COMPLETED fence делает повтор безопасным даже после их удаления. Dispatcher backoff 2 секунды…5 минут, infrastructure cleanup retries без конечного discard. Legacy missing-task repair использует bounded keyset sweep и не застревает на первых десяти документах.

Parsing берёт metadata и принадлежность из DB, отвергает malformed identity до Prisma query, проверяет точный byte count и максимум 10 MiB. Result публикуется лишь при ACTIVE, собственном непросроченном token. Пять попыток; operation cancellation deadline 120 секунд. Expired PROCESSING пятой попытки транзакционно становится FAILED с task DONE; предыдущие crash leases восстанавливаются. Parse lifecycle не объединён с R4 AI accounting.

Upload lease: 10 минут. После него owned cleanup повторяет Delete раз в минуту через 24-часовой quarantine; retryable failure не становится DONE. Это защищает от обычного позднего завершения прерванного Put. Receipts/ledger metadata сохраняются в DB намеренно; автоматическая retention policy для них не введена.

Delete commit сохраняет DELETING и DELETE task. Queries, summary/generation actions и новые parse attempts требуют ACTIVE. Parser и уже queued AI processors проверяют DB scope/lifecycle, а final publication получает guarded document write lock. После S3 success удаляется только tombstoned row своей task. Повторный delete того же workspace использует retained receipt. Flashcards/quizzes/AIJob сохраняют прежнюю SetNull policy; source reference скрывается сразу при tombstone. Полное стирание производных материалов/S3 versions/backups не обещается.

HTTP AI producers используют отдельное соединение, deadline 1500 ms, отключённые offline queue/reconnect/autoresend, закрывают transport и дожидаются завершения операции. Dispatcher producer имеет отдельный предел 3 секунды; consumer сохраняет долгоживущую worker policy. Deadline включает реальную отмену transport, а не один Promise.race. [BullMQ connection policy](https://docs.bullmq.io/guide/connections) и [job identity/removal semantics](https://docs.bullmq.io/guide/jobs/job-ids) учитываются вместе с PostgreSQL fences.

## Ограничения доказательства и production blockers

- Настоящая auth session/login/membership deployment topology R2 не проверяется synthetic route session. Paid AI отсутствует: AI input/output здесь mock, R4 idempotency/accounting и PF-01 demo UI остаются отдельными блокерами. Assistant/dashboard не исправлялись.
- S3/DB/Redis failures внедряются в обозначенных boundaries либо Redis pause; не проводились host power loss, PostgreSQL failover, Redis Cluster/AOF restore, S3 cross-region replication/versions или восстановление backups. Большинство crash windows воспроизводятся остановкой последовательности/failure injection; OS worker restart реален, precise kill в каждой инструкции не выполнен.
- Проверены MinIO conditional Put/HEAD/Delete, а не конкретный production S3/IAM/ingress. Нужны permissions на HEAD/Get/Put/Delete и поддержка conditional create, инфраструктурные backup/retention/eviction/readiness настройки.
- Parse AbortSignal уничтожает PDF parser, но синхронную CPU блокировку PDF engine в общем JS runtime нельзя принудительно остановить. Для hostile-PDF hard runtime limits нужен отдельный process/supervisor или isolation; metadata/signature проверка не заменяет antivirus/content-safety review.
- Leases используют application clocks; hosts должны иметь синхронизированное время. Overdue tasks/leases, final FAILED и cleanup backlog требуют production monitoring. Receipts сохраняются; отдельная reviewed metadata retention policy не введена.
- 24-часовой quarantine предполагает, что прерванный S3 Put не завершается позже этого горизонта. Это операционное допущение, а не доказательство всех storage implementations: перед production нужны подтверждённые provider limits и inventory/lifecycle policy для объектов abandoned uploads; retained ledger позволяет reconciliation. Cleanup failure внутри горизонта и после него продолжает retry до успешного Delete.
- Перед существующей DB migration нужны backup, остановка старых writers и read-only duplicate-key preflight. Duplicate-key DDL откатывается, однако failed Prisma migration receipt требует административного resolve/retry после reviewed remediation. Никакие пользовательские keys не переименовываются и объекты не удаляются автоматически. Прямой административный Workspace/User cascade вне публичных application entrances не является document-delete API.
- Release/CI проверки подтверждают локальный artifact на Windows/Node24; внешний CI/deployment и Linux artifact отдельно. R3 не меняет production NO-GO остальных findings.
