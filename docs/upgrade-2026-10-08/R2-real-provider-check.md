# R2 — отдельная проверка настоящего AI-провайдера

Статус на 8 октября 2026 года: **НЕ ВЫПОЛНЕНА**. Выделенный test project,
подтверждённый лимит расходов и согласованный корпус материалов не предоставлены.
Ключи из рабочих `.env` не читались. Платные запросы при реализации R2 не разрешены
просто наличием ключа в окружении.

## Что уже можно воспроизвести без платных запросов

Из корня репозитория:

```powershell
pnpm --use-node-version=24.21.0 exec node scripts/probe-upgrade-r2-integration.mjs
```

Это отдельный запуск с disposable PostgreSQL 16, Redis 7 и MinIO в Docker.
Используется существующий isolation helper R4: случайные имена и проверяемые
run labels, loopback-порты, tmpfs без постоянных volumes, удаление собственных
контейнеров в `finally`. Рабочие `.env`, compose project и локальный PostgreSQL
не используются. Prisma migrations исполняются из временной копии без `.env`.

Выполняются настоящие upload route handler, S3 PUT/GET, parsing worker, admission
actions, dispatcher, BullMQ worker, Prisma transactions и чтение сохранённых
результатов новой Prisma-сессией. Auth-сессия синтетическая. `AIProvider` использует
явно подставленный in-memory HTTP transport; он возвращает текст источника в
валидной структуре summary/cards. Такой адаптер проверяет доставку полного
содержимого, идемпотентность, ошибки и сохранение, **но не смысловое качество
модели**. Browser fixture отдельно проверяет rendering и действия UI.

Этот скрипт всегда использует тестовый адаптер, даже если на машине есть AI-ключ.
Его нельзя считать проверкой настоящего провайдера.

## Условия допуска отдельного платного прогона

Перед реальным прогоном ответственный должен подготовить проверяемую запись:

- ID отдельного test project у провайдера, отдельный ограниченный ключ и
  подтверждение, что project не используется рабочим сервисом;
- величину и валюту общего **принудительного** spend cap, допустимый остаток и
  механизм немедленной остановки. Budget alert или локальный workspace budget
  не считаются общим ограничением расходов проекта провайдера;
- allowlist модели и разрешённые возможности ключа;
- два небольших разрешённых UTF-8 материала разных тем с указанием прав на
  передачу провайдеру и SHA-256. Короткий выдуманный учебный текст подходит;
  пользовательские документы из рабочего workspace не подходят автоматически;
- ожидаемые факты и недопустимые утверждения для ручной оценки каждого текста;
- ответственное лицо, разрешённое число вызовов, правила retention/удаления.

Если провайдер не позволяет установить требуемый принудительный project cap,
прогон остаётся непроверенным до согласования подходящего контролируемого способа
ограничить расходы. Увеличение лимитов admission ради ответа не допускается.

## Протокол после выполнения условий допуска

1. Создать новое изолированное окружение со свежими PG/Redis/S3, отдельным auth
   test user и workspace. Применить существующие migrations из копии без `.env`.
   Записать только run ID и не секретные policy settings. Секреты передавать
   процессам напрямую; не сохранять их в отчёт, историю команд или screenshots.
2. Запустить настоящий web и worker с разрешённой моделью и прежними конечными
   input/output/attempt/budget ceilings. Убедиться, что provider project ID
   соответствует test project и расход остановится на заданной сумме.
3. Через браузер загрузить первый разрешённый текст; дождаться parsing
   `COMPLETED`. Сгенерировать summary и cards с отдельным ключом на тип операции.
   Повторить запрос с **тем же** ключом: в БД одна logical operation и один
   артефакт. Записать operation IDs, attempt counts, usage/cost и request IDs
   без содержимого приватных prompts.
4. Повторить для второго текста с тем же именем файла. Сверить summary и каждый
   ответ карточек с заранее заданными фактами. Выходы должны различаться по
   содержимому; цитирование правильного источника само по себе не доказывает
   качество педагогической формулировки.
5. Обновить страницу, закрыть и открыть документ заново, затем открыть сохранённый
   набор в настоящем Study. Сопоставить IDs/содержимое с БД. Убедиться, что
   клиентский payload не содержит `parsedText`, storage key или immutable input.
6. В тестовом адаптере отдельно воспроизвести `FAILED` и `UNCERTAIN`; не создавать
   платную неоднозначную ошибку специально. При реальном `UNCERTAIN` прекратить
   автоматические/ручные новые генерации, сохранить тот же ключ и проверить
   ledger/usage у провайдера. Status check не является запросом генерации.
7. Записать итоговый расход test project, даты, модель, результаты ручной оценки,
   ошибки и границы вывода. Остановить процессы и удалить только принадлежащие
   этому прогону ресурсы согласно согласованной retention policy.

Пока этот протокол не выполнен, отчёт R2 должен явно сохранять статус
**real provider NOT RUN** и не заявлять качество AI, готовность платного пилота,
provider billing reconciliation или production readiness.
